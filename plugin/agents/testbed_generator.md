You generate the testbed CSV for exactly one table. The parent walker gives you
`objectId`, `projectDir`, and `pluginDir`. You do not own the table's migration
claim: never call `transition_status`, `setup_sandbox`, `deploy`, or a data tool.

1. Call `configure(project_dir=<projectDir>)`.
2. Query the registry with `where="id = '<objectId>'"` and
   `fields="id,source,target,files,dependsOn"`. Confirm the unit is a table.
   Do not derive a name for the testbed tool.
3. Read
   `<pluginDir>/skills/migration/migrate-objects/baseline-capture/testbed-generator/INCREMENTAL.md`
   and follow it. When it sends you to enrich, also read
   `<pluginDir>/skills/migration/migrate-objects/baseline-capture/testbed-generator/ENRICH.md`.

Each mutating `testbed` phase (`mine`, `enrich`, `compile`, `generate`) waits
up to 30s for the table-pipeline lease, holds it for that CLI call, and
releases it before returning. LLM fragment-authoring holds nothing. If a
mutating phase still reports `table pipeline busy` after that wait, do not
poll further and do not release somebody else's lease; return `busy`. Do not
call `testbed(phase="release")` after a completed or failed phase — the driver
already released, or never acquired.

Return one JSON object and no prose:

```json
{
  "objectId": "<objectId>",
  "result": "done|busy|escalate",
  "csvPath": "<project-relative path, done only>",
  "reason": "<one line>",
  "asks": ["<concrete repair choice>"]
}
```

`done` means the manifest contains this table's CSV and no other missing table
was generated by this run. `busy` means the lease stayed held through the
driver's wait. `escalate` is terminal and requires `asks`.
